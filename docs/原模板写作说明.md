第2章 相关技术

一、章节定位与核心目标

作用：解释项目涉及的关键技术、工具与理论，说明“为什么用这些技术”以及“它们如何支撑项目”。

目标：展现你对技术选型的理性思考，为后续设计与实现铺平道路。

二、章节结构建议（可分2-4个小节）

2.1  总体技术架构概述

用一段文字或框图简要说明项目整体技术栈（如前端、后端、数据库等）。

示例：“本系统采用B/S架构，前端使用Vue.js，后端采用Spring Boot框架，数据库选用MySQL，并通过Docker容器化部署。”

2.2  关键技术分节详解

每项技术建议按以下逻辑展开：

技术简介：是什么？为何流行？（1-2段）

选型理由：结合项目需求说明（如“Vue.js数据绑定特性适合动态管理界面”）。

在本项目中的应用场景：具体用在哪些模块？（如“Spring Security用于实现用户权限控制”）。

技术关联性：如何与其他技术协同（如“Axios实现前后端数据交互”）。

2.3  开发工具与环境

列出关键工具（如IDEA、Git、Postman）。

简要说明用途（如“Jenkins用于持续集成”）。

2.4 （可选）技术难点与解决方案

若涉及特殊技术挑战（如并发处理、算法优化），可提前在此分析。

三、内容撰写要点

1. 避免简单堆砌

❌ 错误：“Vue.js是一个框架，由***开发……”

✅ 正确：“选用Vue.js构建响应式前端，其组件化开发模式便于实现本系统的动态表单模块（见4.2节），同时……”

2. 紧扣项目需求

每项技术都需与项目功能关联（如“选用Redis缓存热点数据，以提升5.3节中的查询性能”）。

3. 适度深入技术细节

对核心技术可适当展开（如Spring Boot的依赖注入机制、MySQL的索引优化原理），但避免过度赘述教科书内容。

4. 善用图表辅助

技术架构图（如分层架构图）、技术对比表（如数据库选型对比）能让表达更清晰。

四、技术选型描述范例

2.1 Spring Boot后端框架

Spring Boot是基于Spring的轻量级开发框架，通过自动配置简化了Java EE应用部署流程。本项目选用Spring Boot 2.7（理由：1. 快速构建RESTful API；2. 内嵌Tomcat服务器便于打包部署）。其在系统中主要用于用户管理模块（详见4.1节）和订单处理接口（详见5.2节），与MyBatis框架整合实现数据持久化操作。

五、常见问题与避坑指南

内容空洞 → 始终关联“本项目的xx模块需要xx技术的xx特性”。

比例失衡 → 重点技术占60%-70%，辅助工具简要带过。

忽视版本 → 精确到具体版本号（如Python 3.9，而非“Python3”）。

技术过时/超前 → 选择主流稳定技术，谨慎使用未成熟方案。

抄袭说明书 → 用自己的语言重新组织，标注参考文献。

六、实用检查清单

1）每项技术都说明了选型理由

2）技术描述与后续章节存在明确呼应

3）图表编号正确、引用准确

4）避免了与“系统设计”章节的内容重复

5）技术术语使用规范，首次出现时附带英文缩写

第3章 需求分析与概要设计

3.1 系统需求分析

目标： 说清楚你要做一个什么样的系统，给谁用，用来干什么。

3.1.1 系统边界与角色定义

· 内容： 明确系统涉及哪些用户群体。

· 写法： “本系统面向三类用户：前台普通游客、前台注册会员和后端管理员。”

· 图表辅助： 画出系统上下文图或简单的用例图，展示角色与系统的交互。

3.1.2 功能性需求

· 内容： 分模块、分角色详细描述系统必须具备的功能。

· 写法： 不要只罗列列表，建议采用 “用例描述” 的方式。

模块一：用户管理模块

· 用例UC-01：用户注册：用户通过手机号和验证码完成注册……

· 用例UC-02：用户登录：……

模块二：核心业务模块

· 图表辅助： 用例图是标配，配合详细的用例规约表（包含：用例名称、参与者、前置条件、基本流程、后置条件）。

3.1.3 非功能性需求

· 内容： 系统的质量属性（体现你的工程素养）。

· 例子：

· 性能要求： 并发用户数、页面响应时间（如：小于3秒）。

· 安全性： 用户密码加密存储、数据传输加密、SQL注入防护。

· 可靠性： 系统7*24小时运行，重要数据备份策略。

· 易用性： 界面简洁，操作符合用户习惯。

3.2 系统概要设计

3.2.1 系统总体架构设计

· 内容： 描述系统的技术栈和分层结构。

· 写法： 如果是Web项目，通常是B/S架构，采用前后端分离。

· 图表辅助： 绘制系统架构图。

· 前端层： Vue/React/小程序，负责界面展示。

· 后端层： Spring Boot/Django等，负责业务逻辑处理。

· 数据层： MySQL/Redis，负责数据存储。

· 基础设施层： 服务器、对象存储等。

· 注意： 要解释为什么选这个架构（如：为了高并发、为了可维护性）。

3.2.2 系统功能模块划分

· 内容： 将3.1节的需求映射成具体的软件模块。

· 写法： 将系统拆分成多个子系统或模块，并说明模块间的调用关系。

· 图表辅助： 绘制功能模块图（分层结构图）。例如：顶层是“在线考试系统”，第二层是“用户端”和“管理端”，第三层再细分。

3.2.3 系统业务流程设计

· 内容： 选取核心业务逻辑，描述数据流转过程。

· 图表辅助： 绘制业务流程图或活动图。例如：“用户下单”的流程：发起支付 -> 检查库存 -> 扣减余额 -> 生成订单。

3.2.4 数据库概念结构设计

· 内容：数据库相关技术架构的概述，具体设计详见第4章。

3.2.5 系统接口设计（可选，但建议写）

· 内容： 如果是前后端分离或涉及第三方系统，列出核心API的设计风格。

· 写法： RESTful风格，简要描述几个核心接口的URL、请求方式、参数和返回值示例。

3.2.6 界面原型设计

· 内容： 展示几张核心界面的低保真或高保真原型图。

· 说明： 简单解释一下界面的布局逻辑和用户操作路径。这能证明你在设计时考虑了用户体验。

写作注意事项：

1. 逻辑对应： 确保概要设计的内容完全覆盖了需求分析中提出的功能。不要让评委觉得“你分析了一堆需求，结果设计出来的模块对不上”。

2. 图文并茂： 这一章最忌讳纯文字。一张好的架构图或E-R图，胜过几百字的描述。建议使用Visio、Draw.io或ProcessOn绘制。

3. 避免过度细节： 这一章叫“概要设计”，不要在这里贴大段的HTML代码、SQL建表语句或具体的算法源码，那是“详细设计”或“系统实现”章的内容。

4. 技术选型要有理由： 不要只是罗列用了Spring Boot、MySQL，要简单说一句为什么（比如：因为Spring Boot生态完善，便于快速开发；MySQL开源且满足数据一致性要求）。

5. 关注核心痛点： 如果你的毕业设计是做“基于深度学习的某某推荐系统”，那么在需求分析时要强调“为什么需要推荐”，在概要设计时要画出“推荐服务的模块位置”和“数据流”。

第5章 详细设计

5.1 系统前端详细设计

5.1.1 前端总体架构

目的：让读者了解前端项目的整体技术选型和结构。

· 开发框架：Vue.js / React / Angular 及其版本。

· UI 组件库：Element UI / Ant Design / Vant 等。

· 状态管理：Vuex / Redux / Pinia / MobX。

· 构建工具：Webpack / Vite。

· 其他工具库：如日期处理（Moment.js / Day.js）、图表库（ECharts / D3）等。

· 前端架构图：绘制前端模块的组织结构，例如： 项目目录结构（src 下按功能划分：components、views、store、router、utils、assets 等）。

· 数据流向图（展示用户交互→视图更新→状态变化→API 请求的完整闭环）。

5.1.2 页面路由与菜单设计

目的：规划系统的页面结构和导航方式。

· 路由表设计：用表格列出所有页面路由，包括：

· 路径（path）

· 对应组件（component）

· 页面名称（name）

· 权限要求（如需要登录、角色限制）

· 嵌套关系（父路由与子路由）

· 菜单导航结构：可以用思维导图或树形图展示系统的菜单层级，说明哪些菜单是动态生成的（根据权限过滤）。

5.1.3 组件设计与用户界面设计

重点：将页面拆分为可复用的组件，体现“组件化”思想。

· 组件划分：

· 绘制组件树，从根组件（App）开始，逐层展示页面级组件、业务组件、通用组件。

· 区分公共组件（如 Header、Footer、Sidebar、Loading）和业务组件（如商品卡片、订单列表项）。

· 核心组件详细设计（选择 2-3 个关键业务组件深入）：

· 组件功能描述。

· Props：接收哪些属性，类型、是否必填、默认值。

· Events：向外触发哪些事件（如点击、输入），携带的数据格式。

· 内部状态：组件自身维护的数据。

· 使用示例：在父组件中如何调用。

· 组件通信方式：简述父子组件通信（props/emit）、跨级组件通信（provide/inject、Context）、全局状态管理之间的分工。

5.1.4 关键交互流程设计

目的：对复杂用户操作进行详细描述，确保前后端理解一致。

· 流程描述：选择 2-3 个核心业务流程（如用户登录、商品搜索、下单支付），用流程图展示用户操作步骤、界面反馈、数据请求时机。

· 界面状态转换：对涉及多步骤的表单或多状态视图，使用状态图说明不同状态下的界面表现。

· 异常处理：如网络错误、表单校验失败时，前端的提示方式和后续行为。

5.2 系统后端详细设计

5.2.1 后端总体架构

目的：让读者了解后端系统的整体技术选型、分层结构和数据流向。

· 技术栈说明：

· 开发语言：Java / Python / Go / Node.js 等。

· 开发框架：Spring Boot / Django / Gin / Express 等。

· 数据库：MySQL / PostgreSQL / MongoDB 等。

· 缓存：Redis / Memcached。

· 消息队列：RabbitMQ / Kafka（如果使用）。

· 其他中间件：Elasticsearch（搜索）、MinIO（对象存储）等。

· 分层架构图：绘制后端逻辑分层，如：

· 表示层（Controller）：处理 HTTP 请求、响应。

· 业务逻辑层（Service）：实现核心业务逻辑。

· 数据访问层（DAO / Repository）：与数据库交互。

· 基础设施层：工具类、第三方集成等。

· 数据流向图：展示一次请求从进入系统到返回响应的完整路径，涉及各层之间的调用关系。

5.2.2 功能模块设计

重点：将系统按业务功能拆分为若干模块，并详细描述每个模块的内部设计。

· 模块划分：

· 列出所有后端模块（如用户模块、商品模块、订单模块、支付模块等）。

· 说明模块间的依赖关系（用模块依赖图表示）。

· 核心模块详细设计（选择 2-3 个关键模块深入展开）：

· 模块描述：该模块负责的功能。

· 类图：展示该模块涉及的主要类（Controller、Service、DAO、实体类）及其关系（继承、关联、依赖）。

· 时序图：描述典型业务流程中对象间的交互顺序（例如“用户下单”涉及 OrderController、OrderService、InventoryService、OrderDAO、PaymentService 等的调用）。

· 流程图：描述模块内部复杂算法或状态转换（如订单状态流转：待支付→已支付→已发货→已完成）。

· 输入/输出说明：接口的请求参数和响应数据（简要说明，详细接口可单独在接口设计部分列出）。

· 其他模块概述：对于非核心模块，简要说明其功能和关键设计点。

5.2.3 安全设计（可选）

目的：保障系统的数据安全和访问控制。

· 认证与授权：

· 认证方式：JWT / OAuth2 / Session-Cookie。

· 权限控制模型：RBAC（基于角色的访问控制），说明角色、权限、资源的定义。

· 实现方式：过滤器/拦截器校验 Token，从 Token 中解析用户信息，结合权限注解（如 Spring Security 的 @PreAuthorize）进行方法级权限控制。

· 数据安全：

· 密码加密：BCrypt / PBKDF2 等哈希算法。

· 传输加密：HTTPS。

· 敏感数据脱敏：如手机号、身份证号在日志和响应中部分隐藏。

· 防攻击措施：

· SQL 注入：使用预编译语句、ORM 框架的内置防护。

· XSS：对用户输入进行转义。

· CSRF：使用 Token 或 SameSite Cookie 属性。

· 接口防刷：限流、验证码等。

5.2.4 部署与运行环境（可选）

目的：简要说明后端系统的部署方案和运行环境要求。

· 硬件/软件环境：服务器配置、操作系统、JDK/Python 版本等。

· 部署架构图：如单机部署、集群部署、负载均衡等（若涉及）。

· 配置管理：配置文件拆分（开发、测试、生产环境），敏感配置（如数据库密码）的加密或使用环境变量。💡

写作技巧与注意事项

1. 图文并茂：

2. 详细设计阶段重点写“打算如何构建”，可以粘贴少量代码。

3. 与需求分析呼应：确保前端设计覆盖了需求分析中的所有界面和交互要求。

· 例如，需求中提到的“用户登录”功能，在设计里要有对应的页面、组件、状态管理、接口调用描述。

4. 突出亮点与难点：

· 如果某个功能有技术挑战（如实时聊天、大屏可视化、复杂表单联动），可以单独展开，详细描述设计方案。如果某个模块有复杂业务逻辑或技术挑战（如秒杀系统、支付对接、实时推荐），可以单独展开，详细描述设计方案，体现你的技术深度和工作量。
